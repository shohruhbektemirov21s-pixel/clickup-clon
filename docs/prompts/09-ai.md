## Prompt

```
Finish (or explicitly scope down) the AI assistant feature for UzWork.
Read frontend/src/components/shell/ai-assistant.tsx FIRST — it is
uncommitted work-in-progress, confirm its current state with git status
before assuming anything below is still accurate.

Ground truth as of the last audit: ai-assistant.tsx has no backend call at
all — it operates purely on data already fetched into the client (tasks,
members, workspace tree) via local heuristics (grouping by due date,
permission-filtered suggestions). There is no apps.ai backend app, no
LLM/AI provider wired into backend/config/settings.py, and no endpoint for
it in docs/API_CONTRACT.md.

Before writing more code, make an explicit decision and document it:
(a) Ship it as a **local heuristic assistant** — no LLM call, just smart
    client-side aggregation of data the user can already see. If this is
    the actual intent, rename/reframe the UI so it doesn't imply an LLM
    is involved (a "Sparkles" icon suggesting AI-generated text over
    heuristic output is misleading), and finish it as a normal frontend
    feature: permission-gated, Uzbek copy, tested.
(b) Wire it to a real backend LLM integration. If so, this needs a new
    ADR (docs/adr/ is out of scope for you unless the architect agent
    is asked separately) covering provider choice, cost/rate-limiting
    (compare to the existing EMAILCHECK_* pattern in settings.py for how
    this codebase gates external-service calls behind explicit env
    config), and prompt-injection/data-exposure risk given the assistant
    would see task/comment content across the permission boundary.

Whichever path, do not claim "AI-powered" in Uzbek UI copy for behavior
that is actually a local sort/filter — that's a trust problem, not just
an accuracy one.
```
